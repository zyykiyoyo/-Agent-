# 多Agent协同运营自动化系统

Multi-Agent Collaborative Operations Automation System

## 一、项目解决的核心问题

### 1.1 痛点

现代企业运营面临以下核心挑战：

| 问题 | 传统方案 | 本系统方案 |
|------|----------|-----------|
| **信息孤岛** | 监控、分析、执行、报告各成独立系统，人工在系统间搬运数据 | Agent间通过消息总线实时通信，数据自动流转 |
| **决策链路过长** | 发现问题→人工分析→制定方案→协调执行→汇总报告，耗时以天计 | 编排器自动分解任务，多Agent并行协作，分钟级完成全链路 |
| **响应滞后** | 依赖人工值班监控，发现异常→定位原因→制定预案→执行恢复，M T T R 以小时计 | 监控Agent实时采集→分析Agent自动检测异常→规划Agent制定策略→执行Agent自动恢复 |
| **经验流失** | 运营策略存在于个人经验中，人员变动导致知识断层 | 推理链和工作流可编程、可复用、可版本化管理 |
| **规模化瓶颈** | 业务增长需要线性增加运营人力 | Agent可水平扩展，通过消息总线增加新Agent类型即插即用 |

### 1.2 核心目标

构建一个 **多智能体协同推理与自动化执行** 的运营系统，实现：

- **感知**：自动采集指标、监控端点、接收告警
- **分析**：趋势分析、异常检测、根因定位
- **规划**：策略制定、任务分解、资源调度
- **执行**：自动化操作、批处理、部署回滚
- **报告**：状态汇总、日报生成、事故复盘
- **闭环**：以上环节通过Agent协作形成自动化闭环

### 2.2 长链推理流程

系统在处理一个复杂运营任务时，经历完整的 **6阶段推理链**：

```
请求入口
   │
   ▼
┌─────────────────────────────────────────────────────────────────┐
│ 第一阶段：任务解析 (Orchestrator)                                 │
│ 输入：用户指令 "检查系统状态并生成运营报告"                          │
│ 推理：解析意图 → 识别子任务 → 确定依赖关系 → 编排执行计划           │
│ 输出：结构化工作流 [监控→分析→规划→执行→报告]                       │
└───────────────────────────┬─────────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────────┐
│ 第二阶段：感知与采集 (Monitor → Analyzer)                        │
│ Monitor: 执行健康检查 → 采集CPU/内存/磁盘/网络指标                  │
│    ↓ 结果传给                                                   │
│ Analyzer: 对指标做趋势分析 → 检测异常(z-score) → 生成诊断结论       │
│ 输出：{"status": "degraded", "anomalies": [...], "insights": []}  │
└───────────────────────────┬─────────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────────┐
│ 第三阶段：策略规划 (Planner)                                      │
│ 输入：分析阶段生成的异常列表和诊断结论                              │
│ 推理：评估影响范围 → 排列优先级 → 制定处理步骤 → 评估资源需求       │
│ 输出：结构化行动计划 {"steps": [...], "resources": {}, "priority"} │
└───────────────────────────┬─────────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────────┐
│ 第四阶段：执行 (Executor)                                         │
│ 输入：Planner生成的行动计划                                        │
│ 执行：按步骤执行(部署/清理/备份/通知) → 记录执行结果 → 异常处理    │
│ 输出：{"action": "cleanup", "status": "completed", "result": {}}  │
└───────────────────────────┬─────────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────────┐
│ 第五阶段：汇总与报告 (Reporter)                                    │
│ 输入：所有前置阶段的结果数据                                        │
│ 推理：结构化汇总 → Markdown报告生成 → 持久化存储 → 通知推送        │
│ 输出：报告文件 + 摘要数据                                           │
└───────────────────────────┬─────────────────────────────────────┘
                            │
┌───────────────────────────▼─────────────────────────────────────┐
│ 第六阶段：反馈闭环                                               │
│ Orchestrator收集全部结果 → 评估整体成功率 → 记录到数据库           │
│ 如有失败环节 → 触发重试或回滚 → 更新系统状态                       │
│ 最终输出：给用户的完整运营报告                                      │
└─────────────────────────────────────────────────────────────────┘
```

### 2.3 多Agent协作模式

本系统实现了 **4种协作模式**，覆盖不同的运营场景：

#### 模式一：编排-执行模式 (Orchestration)
```
Orchestrator ──分解任务──→ Monitor / Analyzer / Planner / Executor / Reporter
     ↑                          │
     └──────── 汇总结果 ←───────┘
```
**适用场景**：复杂运营任务的端到端处理。编排器承担"大脑"角色，负责任务分解、依赖管理、结果聚合。

#### 模式二：流水线模式 (Pipeline)
```
Monitor → Analyzer → Planner → Executor → Reporter
   ①采集     ②分析       ③规划      ④执行      ⑤报告
```
**适用场景**：数据处理流水线。每个Agent的输出是下一个Agent的输入，形成数据处理链。这是典型的长链推理模式。

#### 模式三：查询-响应模式 (Query-Response)
```
Agent A ──发送查询──→ Agent B
         ←──返回结果──
```
**适用场景**：Agent间按需获取信息。例如Planner在执行规划前向Monitor查询最新指标，向Analyzer查询历史趋势。

#### 模式四：广播模式 (Broadcast / Event-Driven)
```
Agent A ──发布事件──→ 所有订阅者
```
**适用场景**：告警通知、状态广播。当Monitor检测到异常时，广播ALERT事件，所有订阅Agent并行响应。

### 2.4 协作流程图解

以下是一个完整的运营自动化流程，展示各Agent如何协同完成"系统巡检-分析-优化"的闭环：

```
时间线
 │
 ├── Orchestrator: 接收任务 "系统全面巡检与优化"
 │
 ├── Orchestrator → Monitor: 【编排】第一步 - 执行系统健康检查
 │   ├── Monitor: 采集CPU/内存/磁盘指标
 │   ├── Monitor: 检查配置的端点可达性
 │   └── Monitor → Orchestrator: 返回指标数据
 │
 ├── Orchestrator → Analyzer: 【编排】第二步 - 分析采集的数据
 │   ├── Analyzer: 对CPU指标做趋势分析
 │   ├── Analyzer: 检测异常值(z-score>2)
 │   └── Analyzer → Orchestrator: 返回分析结论
 │
 ├── Orchestrator → Planner: 【编排】第三步 - 制定优化方案
 │   ├── Planner: 【查询】向Monitor请求历史数据
 │   ├── Planner: 【查询】向Analyzer请求异常详情
 │   ├── Planner: 综合信息制定处理步骤
 │   └── Planner → Orchestrator: 返回行动计划
 │
 ├── Orchestrator → Executor: 【编排】第四步 - 执行优化
 │   ├── Executor: 执行清理操作
 │   ├── Executor: 执行备份操作
 │   └── Executor → Orchestrator: 返回执行结果
 │
 ├── Orchestrator → Reporter: 【编排】第五步 - 生成报告
 │   ├── Reporter: 汇总所有阶段的输出
 │   ├── Reporter: 生成Markdown报告并保存
 │   └── Reporter → Orchestrator: 返回报告路径
 │
 └── Orchestrator: 【闭环】评估整体结果，记录到数据库，标记完成
```

## 三、快速开始

```bash
# 1. 安装依赖
pip install -r requirements.txt

# 2. 启动系统（含Web仪表盘）
python main.py

# 3. 运行演示脚本（展示完整的多Agent协作推理链）
python demo.py

# 4. 无界面模式
python main.py --no-dashboard

# 5. 自定义端口
python main.py --port 9090

# 6. 调试模式
python main.py --debug
```

打开浏览器访问 `http://localhost:8080` 查看实时仪表盘。

## 五、配置

编辑 `config.yaml` 调整系统参数：

```yaml
agents:
  monitor:
    check_interval: 60        # 检查间隔(秒)
    endpoints:                # 监控的端点列表
      - "http://localhost:8080/health"
  analyzer:
    anomaly_threshold: 2.0    # 异常检测阈值(z-score)
  executor:
    retry_on_failure: true    # 失败自动重试
    max_retries: 3
```

## 九、设计理念

1. **Agent自治性**：每个Agent独立运行，通过消息通信，不共享状态
2. **异步非阻塞**：所有I/O操作使用asyncio，支持高并发
3. **可扩展性**：添加新Agent只需继承BaseAgent并实现execute_task
4. **容错性**：单个Agent失败不影响系统整体运行
5. **可观测性**：所有消息、任务、状态均可追踪和回放
